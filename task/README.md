# Skyforge Forum Downloader Task

This task drops the agent into `/workspace` with a small Python downloader project and a local forum running at `http://localhost:8080`. The agent is told only that `./bin/download-mods --forum-url "$FORUM_URL" --target "Skyforge Overhaul" --out downloads/` currently produces the wrong archive set. The actual work is to diagnose forum prose, fix dependency/version resolution, and make a clean rerun download exactly the required release archives.

The environment is intentionally shaped so the failure is not a one-line filter bug. The visible fixture has a pinned reply on the Skyforge thread that narrows CoreLib to `1.4.0`, a normal reply on the ScriptBridge thread that pins Linux users to `5.1.2`, optional companion/source/screenshot archives mixed in with the real release links, prerelease attachments with larger version numbers, and range/line-lock constraints like `2.0.x only`, `v5.1 exactly`, and `>=0.9.5, <1.0`. The downloader project ships broken logic in `modsync/dependencies.py` and `modsync/versioning.py`; the seeded code only reads the OP for dependency text, treats every `.zip` attachment on a thread page as a release candidate, parses versions out of any filename fragment, mishandles `X.Y exactly` and `X.Y.x`, ignores prereleases, and picks the max version string. `modsync/engine.py` then downloads every unconstrained candidate on the target page and recurses without combining repeated constraints, so a fresh run actually leaves a noisy `downloads/` directory for the agent to inspect. The oracle patch in `task/solution/solve.sh` rewrites all three modules.

The forum is a real local HTTP service, not a stubbed CLI. `task/environment/payload/forum/forum_seed.py` defines both the visible and hidden fixtures. `generate_forum_assets.py` materializes valid ZIP files containing deterministic `MOD_INFO.txt`, `run_server.py` serves `/`, `/thread/{slug}`, `/search`, and `/attachments/{filename}`, and `forum_serverctl` plus `/etc/profile.d/forum_env.sh` keep the server running for both the agent and the verifier. `sanity_check.py` runs during Docker build to confirm the visible correct set is `{skyforge-overhaul-3.4.1.zip, corelib-1.4.0.zip, terrainkit-2.0.5.zip, weatherhooks-0.9.8.zip, scriptbridge-5.1.2.zip}` and that the broken resolver falls into the intended traps. `build_manifest.py` records SHA256 hashes for protected files, forum JSON, and all served ZIPs.

The verifier in `task/tests/test_outputs.py` does four phases: visible run, visible rerun for determinism, hidden-fixture rerun, then protected-file integrity. It never imports the agent’s source. Instead it scrapes the live forum with its own small oracle resolver to compute the hidden expected set from the hidden prose, and it compares each downloaded archive hash to the bytes served by `/attachments/...`. Protected-file integrity covers the fixed entrypoint `/workspace/bin/download-mods`, package metadata (`pyproject.toml`, `uv.lock`), the forum startup/server helpers, both fixture JSON files, and every ZIP attachment under `/opt/localforum/fixtures/`.

Expected solution path:

- Inspect the local forum pages carefully, including replies and badges.
- Fix the dependency walker so replies participate, dependency constraints accumulate, and optional/source/media attachments do not become release candidates.
- Fix version semantics so line locks and wildcard branches become bounded ranges, prereleases are excluded, and exact Linux pins from replies override “latest stable within range”.
- Rerun the documented command from a clean `downloads/` directory and confirm the five required ZIPs are the only outputs.
